**Date:** 2026-07-11

## TL;DR

The fix correctly diagnoses the "WS MATCHED but qty=0" bug and adds a real REST
fallback. **However there is one critical bug that MUST be fixed before
deployment**: `clob.get_order_filled_size` returns Polymarket CLOB base-units
(fixed-math, 6 decimals) but the code does not divide by `1_000_000`, so the
engine will treat e.g. a 5.71-share fill as 5,710,000 shares. Position state
will be wildly wrong (cost basis 1,000,000× too high). Several smaller issues
are listed below.

**Recommendation:** fix the base-unit bug first, then redeploy. Everything else
can ride along.

## Critical bugs (block deployment)

### C-1. `get_order_filled_size` does not convert base units → shares

**Severity:** CRITICAL
**File:** `src/execution/clob_client.py` lines 304–342
**Impact:** If the REST fallback path fires (which is the entire point of the
fix), every fill is mis-scaled by a factor of 1,000,000. Engine position state
becomes useless, unrealized PnL is meaningless, TP arithmetic overflows.

**Why it's wrong:**

The Polymarket CLOB REST endpoint `/data/order/{id}` returns numeric fields
in **fixed-math base units** (6 decimals, micro-shares / micro-USDC). Same
convention is already used elsewhere in this codebase — see
`get_pusd_balance` at line 287-288:

```python
bal = await self._run(self._client.get_pusd_balance)
return float(bal) / 1_000_000 if bal else 0.0
```

Polymarket docs:
> The `size_matched` field is a string representing the quantity of tokens
> filled in fixed-math format with 6 decimal places. For example, a fully
> filled order of 100 tokens returns `size_matched: 100000000`.
> [https://docs.polymarket.com/api-reference/trade/get-single-order-by-id]

So a 5.71-share fill returns `"size_matched": "5710000"`. Our code:

```python
for k in ("size_matched", "sizeMatched", "amount_matched",
          "amountMatched", "filled_size", "filledSize"):
    v = resp.get(k)
    if v is not None:
        try:
            f = float(v)
            if f > 0:
                return f   # ← returns 5710000, not 5.71
```

**Fix:**

```python
_BASE_UNITS = 1_000_000  # Polymarket CLOB uses 6-decimal fixed-math

for k in ("size_matched", "sizeMatched", "amount_matched",
          "amountMatched", "filled_size", "filledSize"):
    v = resp.get(k)
    if v is not None:
        try:
            f = float(v)
            if f > 0:
                return f / _BASE_UNITS
        except (TypeError, ValueError):
            continue
return 0.0
```

Note: if the field name is `amount_matched` (USDC notional), division by
1,000,000 still applies (micro-USDC = 6 decimals, same as `get_pusd_balance`).

**Action:** Fix and redeploy before any live round tries the REST path.

### C-2. Existing `place_gtd_buy` polling has the same bug (pre-existing, not introduced by H-V6-12)

**Severity:** HIGH (pre-existing)
**File:** `src/execution/clob_client.py` lines 444–453
**Impact:** When the synchronous post-response returns without fills and the
polling loop is what discovers the fill, `total_sz` is summed from
`fills[].size` in base units. The fill `total_usdc` then uses
`sum(sz * px)` which inflates `usdc` by 1,000,000 as well, so the
`avg_px = total_usdc / total_sz` actually cancels out and price comes out
right — but `tokens` is wildly inflated.

Note: this path is **only** taken when the WS never delivers a fill event for
a GTD order, which after H-V6-12 should now be very rare. So this latent
bug is mostly masked, but if it ever fires it would still produce wrong
`total_sz` → wrong `FillResult.tokens`.

**Fix (optional in this PR, can ride):** divide each `f.get("size", 0)` by
1,000,000 in the polling loop, then also re-scale
`_round_down(total_sz, Decimal("0.0001"))` accordingly.

**Action:** Optional follow-up; document as known limitation.

## Medium bugs (should fix before next audit)

### M-1. `_trade_dump_count` is not reset on WS reconnect

**Severity:** MEDIUM (operator-visibility)
**File:** `src/market/user_ws.py` lines 245–258
**Impact:** Debug dump only fires for the first 5 trade messages **per bot
lifetime**, not per WS connection. After a single reconnect (which happens
whenever the user WS drops, e.g. heartbeat timeout), no further dumps are
emitted even if the WS payload shape changes. The whole point of the dump is
to discover the size-field quirk; we want one dump per connection to be safe.

**Fix:**

```python
# in __init__
self._trade_dump_count = 0

# in _run(), after successful connect (around the websockets.connect context):
self._trade_dump_count = 0
```

**Action:** Init in `__init__` and reset on each successful connect.

### M-2. `delta` computation double-counts REST cumulative fills on duplicate events

**Severity:** MEDIUM (only matters if a MATCHED event fires twice for same order)
**File:** `src/main.py` lines 991–999 (callback in `_make_maker_fill_callback`)
**Impact:** When the REST fallback returns the cumulative `size_matched`, the
router adds it to `new_cumulative = prev + fill_size_inc`. The deduper
compares `new_cumulative - prev_cumulative` to 1e-9 — but for REST-driven
events, `new_cumulative` is wrong (it's `2 × size_matched`, not
`size_matched`). The deduper won't catch the second MATCHED event because
`2x - x = x > 1e-9`, and `delta = fill_size_inc = x` gets forwarded a
second time → engine double-counts.

This is partially masked by the B-3 deduper's *intent* (treat UPDATE-style
events as deltas), but the math is wrong when input is cumulative.

**Fix:**

Either (a) in `user_ws._handle_trade`, when REST fallback fires, also
remember the previous cumulative so the router can compute the true delta,
or (b) drop the deduper math and always send `delta = fill_size_inc` (the
current behaviour) but track which orders have already had a REST-resolved
fill event so the second event becomes `delta = 0`.

The simplest correct semantics: **after the first REST-resolved fill for a
given order, suppress all subsequent WS trades for that order until a new
round**. Track via a small set on UserWS:

```python
self._rest_resolved_orders: set[str] = set()

# in _handle_trade after REST fallback fires successfully:
self._rest_resolved_orders.add(mo_id)

# before emitting, check:
if mo_id in self._rest_resolved_orders:
    return  # already accounted for via REST
```

**Action:** Either fix the deduper math or add the suppression set.
Defer if rare in production.

### M-3. `cancel_orders` should be wrapped in try/except for connection errors

**Severity:** MEDIUM
**File:** `src/execution/clob_client.py` lines 537–557
**Impact:** If CLOB is unreachable when we try to cancel a timed-out GTD, the
`except Exception` catches it and we log `poll_timeout_cancel_failed` but
**also** fall through to `return FillResult(success=False)`. The function
already handles this — actually re-reading, the try/except IS correct.

But there's a subtler issue: `_run` itself uses `run_in_executor` which can
throw `concurrent.futures.CancelledError` on shutdown. That's not caught by
`except Exception` (CancelledError inherits BaseException in py3.8+). During
shutdown, the cancel call could raise an uncaught exception that breaks the
`finally` / cleanup chain. Low risk but worth noting.

**Action:** No-op unless we see shutdown crashes.

### m-2. `router.maker_fill.skip` log message is misleading

**Severity:** LOW
**File:** `src/main.py` lines 967–971

```python
log.info(
    "router.maker_fill.skip",
    order_id=order_id, fill_size=fill_size_inc,
    reason="WS size=0 + REST fallback returned 0/None",
)
```

The message says "WS size=0 + REST fallback returned 0/None" but actually
the router itself does not know whether the REST fallback was tried —
that's `user_ws`'s concern. By the time the router sees the fill, either
(1) the REST fallback filled a 0 → still 0, or (2) the REST fallback also
failed. The router can't tell. The message should say something like
`reason="received size=0 fill from upstream"` and let `user_ws` log the
REST fallback decision separately.

**Action:** Reword the reason string.

### m-3. STATUS print lacks info when `entry_side` is None

**Severity:** LOW
**File:** `src/main.py` lines 686–703

When `pos.entry_side is None` (before first fill), the line prints
`side=- tiers=[...] qty=0.00 avg=0.0000 cost=$0.00 mid=0.0000 uPnL=$+0.00`.
The `uPnL=$+0.00(+0.0%)` is unhelpful — `pnl_pct_str` is correctly gated by
`pos.total_qty > 0` so the percent is empty, but the dollar is still
printed as `+0.00` which looks like a real zero, not "no position yet".

**Fix:** print `uPnL=$0.00` (no `+` sign) when `pos.total_qty <= 0`.

## Things that look fine

- The dual-pass strategy (try WS keys → fall back to REST) is the correct
  order: REST has latency (~50-200ms) so we want to use the WS value when
  present.
- The `_run` executor pattern in CLOBClient ensures the REST fallback
  inside `_handle_trade` does not block the WS event loop. Good.
- The STATUS line addition (side/avg/mid/uPnL) is straightforward and
  correctly uses `position.entry_side` which is already maintained by the
  engine. No new state surface added.
- The `cancel_orders([{"orderID": oid}])` format matches what the existing
  batch-cancel path at line 868 uses successfully.
- `_extract_size_from_payload` correctly handles string-encoded numbers
  ("5.71" via `float(v)`).
